The one law

the editor
mounts the output onto the canvas and makes it typeable
→ctx→
render(doc, theme, ctx)
a pure function of the document. src/render.js
←ctx←
the SCORM export
serialises the same output into a package

What you see in the editor is what ships. Both consumers call one render, so they cannot disagree. Nothing in the editor or its stylesheets may leak into render(); new per-document state is data on the doc, never editor state. If a change would make the editor and the export diverge, it is wrong.

The context is the seam. It used to be ten window.__* globals assigned by hand in two files, with no test crossing between them — so a divergence was an omission nobody could see. src/render-context.js builds it once; the editor and the exporter are its two adapters, and a test asserts the two contexts are deep-equal.

Start here, by what you are doing

Add a block type

  1. Add its row to src/blocks/manifest.js first
  2. Run node tests/run.js — it names the pieces you have not written
  3. Write each: render, CSS, runtime, inspector

Change an inspector panel

  1. src/editor/inspector/blocks.js — the block-type table
  2. Controls come from inspector/primitives.js; a hand-rolled row is a defect
  3. Not a block? parts.js (field, grid instance) or scopes.js (document, page, multi)

Change how the canvas behaves

  1. world.js builds and paints it
  2. editing.js makes it typeable — the pure-render invariant is really about this file
  3. selection.js, drill.js, dnd.js for what a click does

Change chrome styling

  1. styles/editor/ — 14 files, joined in order.json order
  2. Adding a file means adding its row; the suite gates both directions
  3. Course output is styles/course/ and never the same file

Move code out of editor.js

  1. Read src/editor/kernel.js's header — five rules, each a shipped bug
  2. need() resolves against provide(), never another module's expose()
  3. Route writes to a live binding through its setter before rewriting reads

Work out where something lives

  1. src/editor/README.md — one row per module, gated so it cannot rot
  2. Then this page's module index below
  3. Grep last

The layers

src/render.js3,784 lines

The pure core, and the one genuine seam that predates everything else: BLOCKS, a table from block type to DOM. Loads before anything that uses it. It knows nothing about the editor.

src/*.js~40 files

The shared engine both the editor and the exported course use: runtime.js and quiz-runtime.js (learner behaviour), export.js (the SCORM package), persist.js, schema.js, model.js, source-doc.js, theme.js. Classic scripts, most with a dual-mode footer so tests can require the real thing.

src/editor.js6,657 lines

The host. Almost entirely wiring now: the bind table, the provide / provideLive surfaces, the install() calls and the init block — plus the canvas mount, input handling, and the substrate that three or more surfaces read (selection, world, doc). It was 26,176 lines.

src/editor/58 modules

Everything else, reached through kernel.js (window.VersoEditor). A module declares what it needs and exposes its entry points; the host provides. Most are install(kernel); two (product-rail.js, dnd.js) are pure models with no install.

styles/ · docs/guide/45 files

Three directories of split files, each joined in the order its order.json declares — the browser concatenates the chrome CSS via <link>, the exporter inlines the course CSS into the one course.css that ships, and one loader joins the guide. Order is part of the source, because CSS cascades.

A block is four registries and a manifest

Adding a block used to mean four edits in four files in four different idioms with nothing checking you did all four. Each concern is a table keyed by block type now, and src/blocks/manifest.js declares which of them a given type has.

ConcernRegistryLives inTypes
Renders to DOMBLOCKSsrc/render.js27
Course styling (ships in SCORM)—styles/course/25
Learner behaviourRUNTIMEsrc/runtime.js7
Inspector panelINSPECTORSsrc/editor/inspector/blocks.js18

Not every block has all four, and the manifest says so explicitly. A heading renders and is finished. Course chrome that binds to the page rather than to a block goes in CHROME_RUNTIME, kept separate so “this block has no runtime” and “this runtime has no block” stay distinguishable. The suite checks every claim in both directions.

What the tests enforce

Three tiers, in order of preference: require the file → tests/_load.js (a node:vm context, for files a require cannot reach) → tests/_editor.js (boots the whole editor). Reading source text and slicing a core back into life is below all three — it is what once made the harness forbid restructuring.

Three things a green suite cannot see

Each of these shipped past 5,000+ passing assertions

  • A relative URL that stops resolving when a file moves. A test that reads CSS text cannot see a 404. Load the page in a browser and watch the network.
  • A free identifier that only throws on one path. A moved region's functions live inside install(), so a call site nobody rewired is invisible until that path runs. The orphan gate exists for this.
  • A window.Verso* global that is already taken. Nothing checks globals. Grep for the name before you publish a new one.
